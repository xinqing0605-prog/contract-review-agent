# 04 · 架构设计

## 分层

```
┌─────────────────────────────────────────────┐
│ web/  React 19 + TS + Vite + Tailwind       │
│  · useSession（登录态）  · useWorkspace（业务）│
│  · 偏移量渲染（原文高亮） · SSE 消费          │
└──────────────────┬──────────────────────────┘
                   │ 同源 HTTP / SSE
┌──────────────────▼──────────────────────────┐
│ app.py      路由 · 业务编排 · 静态资源托管    │
│ auth.py     注册登录 / 会话依赖               │
│ model_config.py  服务商与模型 / 模板          │
│ provider.py  OpenAI 兼容客户端               │
│ detector.py  条款规则（纯标准库）             │
│ ingest.py    文件解析（PDF/Word/文本）        │
│ security.py  密码哈希 / 令牌 / Key 加密       │
│ db.py        建表 / 迁移 / 演示数据           │
└──────────────────┬──────────────────────────┘
                   │
              SQLite + data/
```

设计原则：**越往下越稳定，越往上的越可替换**。`detector.py` 不依赖 FastAPI，所以能被评测脚本直接导入；`provider.py` 不依赖数据库，所以换服务商不影响业务层。

## 一次审阅的数据流

```
POST /review 或 GET /review/stream
        │
        ├─ 1. 校验归属（owned_document → 404）
        ├─ 2. 生成步骤事件（SSE 逐条推送）
        │     step: 读取文档
        │     step: 条款切分   ← detector.analyze_text
        │     step: 模型审阅   ← provider.complete_json（可失败降级）
        │     step: 风险分级
        │     step: 生成建议
        └─ 3. 落库：clauses 全量重建（保留人工结果）+ audit + status
                │
                └─ result 事件携带完整 JSON
```

**为什么用事件流实现**：同一份生成器既服务 JSON 接口又服务 SSE 接口，避免两条链路的逻辑漂移。JSON 接口只是"把事件收集起来返回最后一个"。

## 坐标体系（最容易出错的地方）

条款的 `start_offset / end_offset` 是**相对于正文的字符下标**，前后端共用：

```
原文:  甲方应在...九十日内支付全部款项。
        └──────── 0..35 ────────┘
clause.start_offset = 0
clause.end_offset   = 35
clause.original     = text.slice(0, 35)   // 必须严格相等
```

三条硬约束：

1. 后端 `sentence_span()` 把命中扩展到**整句**，前后端粒度一致
2. 写入时 `original` 直接取切片，不重新生成 → 杜绝"模型编造原文"
3. 前端 `buildSegments()` 处理重叠时裁剪后一段，不产生嵌套 `mark`

自检方式：`GET /api/documents/{id}/text` 拿到正文，逐条比对 `text.slice(start,end) === original`。

## 为什么检测用规则、生成用模型

| 维度 | 规则 | 模型 |
| --- | --- | --- |
| 可复现 | 同一合同每次结果一致 | 有随机性 |
| 回归测试 | 可写断言 | 难写断言 |
| 成本 / 延迟 | 0 / <1ms | 按 token 计费 / 秒级 |
| 语义理解 | 弱（关键词） | 强 |

结论：**检测（要可审计）交给规则，解释与建议（要可读）交给模型**。模型失败时降级为规则文案，业务不中断。

代价是召回有限：`单方解除且无需补偿` 这类没有关键词的条款会漏。评测集里专门留了这条用例。

## 多租户隔离

```
users
  └── documents(user_id)          ← 归属校验入口
        └── clauses(document_id)  ← 只能经 documents 访问
  └── model_services(user_id)
        └── service_models        ← 只能经 services 访问
  └── review_audit(user_id)
```

- 所有查询带 `WHERE user_id = ?`
- 越权统一返回 **404 而不是 403**（403 会泄露"这个 id 存在"）
- 条款没有 `user_id`，通过 `JOIN documents` 校验，避免两套真相

## 部署形态

**单容器同源**：FastAPI 同时提供 API 和 `web/dist` 静态资源。

好处：
- 没有跨域，Cookie 天然同源
- 一套部署，一个域名
- 不存在"前端能开、后端没起"的半死状态

代价：改前端要重新 `npm run build`（开发时用 5173 代理规避）。

## 关键取舍记录

| 决策 | 选择 | 放弃的方案 | 原因 |
| --- | --- | --- | --- |
| 认证 | 服务端会话 + httpOnly Cookie | localStorage JWT | XSS 偷不走令牌，可服务端吊销 |
| 密码 | PBKDF2（标准库） | bcrypt / argon2 | 不引入原生依赖，24 万次迭代足够 |
| 数据库 | SQLite | Postgres | 单机部署零运维；已隔离好，换库成本可控 |
| 模型调用 | 裸 urllib | openai SDK | SDK 强制绑定其协议版本，裸 HTTP 对兼容端点更宽容 |
| 条款粒度 | 句子 | 词语 ±N 字符 | 高亮必须与原文严格对齐，词语窗口必然错位 |
| 前端状态 | React hooks + 手写状态机 | Redux / 状态库 | 状态规模不足以引入门槛 |
